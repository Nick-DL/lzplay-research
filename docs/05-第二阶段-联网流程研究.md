# 旅游必备 / Chat Partner 联网流程研究（第二阶段 · 第 1 步）

> 目的：弄清两个 App 的完整工作流程与时序，判断**哪些步骤必须联网**，
> 从而确定 VPN 代理需要伪造哪些响应 —— 以取代"备份还原 + 手工收集 APK"。
>
> **结论先行：需要联网的步骤比预想的少得多，而且核心的 GMS 包清单就在 APK 里。**

---

| 3 | `http://cdn-trip-happy.sg.ufileos.com/…`<br>`http://cdn.trip-happy.com/…` | GMS APK 下载 | ☠️ **CDN 已下线** |

**只有第 1 和第 3 需要伪造。第 2 是 Google 官方接口，不需要伪造。**

## 二、关键发现①：GMS 包清单**内置在 APK 里**，不联网

`com/x/plus/pro/update/c.smali` 的 `a(Context) → List<ApkInfo>`：

```java
// SDK_INT == 28 ? "Xpp_P.json" : "Xpp_Q.json"
String name = (Build.VERSION.SDK_INT == 28) ? "Xpp_P.json" : "Xpp_Q.json";

// c.b = "abksfsijifefe"  ← 硬编码密钥
RC4 rc4 = RC4Factory.a(c.b);

// 从 assets 读加密文件 → RC4 解密 → Gson 解析
String plain = rc4.a(FileUtil.a(ctx, name));
ConfigBean cfg = gson.fromJson(plain, beans.config.a.class);
return cfg.a;                        // List<ApkInfo>
```

### 解密算法（完全还原）

```java
// com/x/plus/pro/b/c.smali  (RC4JavaxImpl)
static { a = new String(Base64.decode("UkM0", 0)); }   // "UkM0" → "RC4"

String a(String td) {
    byte[] b = Base64.decode(td, 0);
    SecretKeySpec k = new SecretKeySpec(this.b /* key bytes */, a);
    Cipher c = Cipher.getInstance(a);
    c.init(DECRYPT_MODE, k);
    return new String(c.update(b));
}
```

⇒ **`明文 = RC4( Base64解码(assets/Xpp_Q.json) )`，密钥 `abksfsijifefe`，无 IV。**

工具：`work/tools/decrypt_xpp.py`（纯 Python 实现 RC4，已跑通）

## 四、关键发现③：没有服务器密钥，响应签名可自行伪造

更新接口用 POST，请求体是**明文 UTF-8 JSON**：

```java
// c.a(Context, url) 构造请求体
JSONObject body = new JSONObject();
body.put("uuid",         DeviceUtil.a(ctx));    // 设备 uuid
body.put("brand",        Build.BRAND);
body.put("model",        Build.MODEL);
body.put("product",      "Trip");
body.put("time",         String.valueOf(System.currentTimeMillis()));
body.put("sign",         c.g);                  // ← 见下
body.put("os",           "Android");
body.put("os_version",   Build.VERSION.SDK_INT);
body.put("language",     <locale 语言>);
body.put("region",       <locale 国家>);
body.put("wifi",         NetworkUtil.b(ctx) ? "1" : "0");
body.put("version_code", String.valueOf(PackageUtil.d(ctx, ctx.getPackageName())));
body.put("version_name", …);

// 然后 c.a(JSONObject.toString().getBytes("utf-8"))
//      —— 纯 UTF-8 编码，没有加密、没有压缩
```

### 请求签名的算法

```java
// c.a(HashMap<String,String>)
String[] keys = map.keySet().toArray();   // 取全部 key
Arrays.sort(keys);                        // 按字母序排序
StringBuffer sb = new StringBuffer();
for (String k : keys) sb.append(k).append("=").append(map.get(k));   // 无分隔符拼接
sb.append("XPP");                                                    // 固定后缀
return StringUtil.b(sb.toString());       // = MD5，小写 hex
```

⇒ **`sign = MD5( "brand=…model=…product=Triptime=…uuid=…" + "XPP" )`**
（参与签名的只有那 5 个字段，全部按字母序）

`StringUtil.b` 就是标准 `MessageDigest.getInstance("MD5")` + 小写 hex。

### 响应校验

```java
// UpdateImp$1.a(Object)  —— 收到响应
JSONObject root = new JSONObject(JsonUtil.a(raw));
JSONObject data = root.getJSONObject("data");
String conf = data.getString("upgradeConf");
String sign = data.getString("upgradeConfSign");

String expect = MD5( MD5_hex(conf) + c.b() );   // c.b() 返回 c.g
if (!sign.equals(expect)) { /* 校验失败 */ }
```

**关键**：`c.g` 是**本次请求自己算出来的 sign**（在 `a(Context,url)` 里被赋值
`sput-object v1, c->g`），而 `c.b()` 就返回它。

⇒ **校验用的"密钥"是客户端自己生成的，不是服务器下发的。**
⇒ **代理可以伪造任意 `upgradeConf` 并自算合法的 `upgradeConfSign`。**

## 五、关键发现④：设备注册的 JS **也是内置的**（推翻我早先的判断）

早先我看旅游必备的 `RegisterActivity` 代码，看到：

```java
c.s.a.g.j.INSTANCE.get(url)   // 取 JSONObject
json.getString("register_js") // 取字段
webView.loadUrl(js)
```

就推断"JS 是从服务器下载的"。**这是错的。**

实际情况（Chat Partner `c/s/a/g/i.smali` 方法 `c()`）：

```java
String tmpl = d();                          // ← 一个硬编码的 base64 常量
String js   = String.format( new String(Base64.decode(tmpl)), gsfId );   // 填入 GSF ID
json.put("register_js", Base64.encode(js.getBytes()));                   // 重新 base64
c.s.a.g.j.INSTANCE.add("https://www.google.com/android/uncertified", json);  // 存进【本地】缓存
```

`c/s/a/g/j.smali` 只是个 **Enum 单例 + HashMap 的内存缓存**，`get()` 是纯本地读。
`add()` 全工程只有一处调用者，就是上面这段。

⇒ **JS 是 App 自带的常量，唯一动态部分是嵌入的 GSF ID。完全不联网。**

### 提取结果

| 文件 | 大小 | SHA-256 |
|---|---|---|
| `work/register/ChatPartner_register_0.js` | 1685 B | `bf57f30fa841d614…` |
| `work/register/旅游必备_register_0.js` | 1685 B | `bf57f30fa841d614…` |

**两个 App 用的是逐字节相同的同一份脚本。**

### 脚本逻辑（全文见 `work/register/*.js`）

```javascript
javascript:(function() {
    // 1. 先数一遍页面上现有的"已注册设备"条目（带 role=option + tabindex 的 span）
    var spans = 0;
    for (...) if (span[i].role == 'option' && span[i].hasAttribute('tabindex')) spans++;

    // 2. 把 GSF ID 填进第一个输入框
    var input = document.getElementsByTagName('input');
    input[0].value = '%s';                       // ← GSF ID 在这里注入

    // 3. 找到 role=button 的 div 并点击（提交）
    for (...) if (vec[i].role == 'button') { vec[i].click(); isClick = true; }

    // 4. 每 2 秒轮询一次，最多 10 次；条目数比初始值多 1 个就判定成功
    registerFun = setInterval(function(){
        if (counts > 0) {
            counts--;
            if (tspans - spans >= 1) { clearInterval(registerFun); window.android.registerResult(0); }
            else                     { window.android.registerResult(1004); }
        } else { clearInterval(registerFun); window.android.registerResult(-1); }
    }, 2000);
})()
```

**成功码 `0`；错误码 `1001/1002/1003/1004/2001/2002/-1` 分别对应各种页面结构不符。**

### 结论：这直接就是 SafeNet 问题的解法

`window.android.registerResult(0)` 即"注册成功"。
**这个脚本本身就是一份可复用的"自动填写 Google 未认证设备注册页"的自动化代码**，
而且已经被这两个 App 在真实设备上验证过（用户的 Mate50 就是靠它注册的）。

⇒ **第二阶段第二个问题（SafeNet 认证）不需要重新发明，
只需要把这份脚本 + GSF ID 交给 WebView 执行即可。**
我们自己的 LZRevive 完全可以照做。

## 六、完整时序（哪些步骤必须联网）

```
SplashActivity
    │
    ├─ 读 SharedPreferences 判断是否已注册
    │     └─ 未注册 → RegisterActivity（WebView 打开 Google uncertified）  ← 🌐 联网(Google)
    │            └─ WebViewClient 回调时向自家服务器取 register_js(JS 脚本)
    │                   └─ 服务器已死 ⇒ 这一步现在拿不到 JS                      ← ☠️ 需伪造
    │
LauncherActivity
    │
    └─ InstallActivityNew
          │
          ├─ UpdateInstance.a(ctx)  更新检查 POST api.trip-happy.com     ← ☠️ 需伪造(可选)
          │
          ├─ UpdateInstance.c(ctx)  读 assets/Xpp_Q.json → RC4 解密        ← ✅ 本地，不联网
          │                        得到 5 个包的清单
          │
          ├─ 逐个 FileDownloader 下载 downUrl 指向的 APK                   ← ☠️ 需伪造
          │     com.liulishuo.filedownloader，校验 fileMd5
          │
          ├─ DevicePackageManager.installPackage(cn, path)  安装            ← ✅ 本地
          │
          └─ 注册/激活                                                     ← 见 SafeNet 部分
```

### 逐项判定

| 步骤 | 必须联网？ | 代理要做什么 |
|---|---|---|
| 更新检查 `upgrade/info/` | ⚠️ **不一定** —— 失败时走本地清单兜底 | 可返回"无更新"的最简合法响应 |
| **读 assets 包清单** | ❌ **完全不需要** | 不用管 |
| **下载 GMS APK** | ⚠️ **需要，但可以换源** | 把 CDN 请求重定向到本地文件 |
| 安装 / MDM 提权 | ❌ 本地 | 不用管 |
| 设备注册（Google uncertified） | ✅ 但那是 Google 官方 | **不要伪造**，见 SafeNet 研究 |
| `register_js`（自家服务器下发的 JS） | ☠️ 服务器已死 | **需要伪造**（或绕过注册态检查） |

## 七、对方案的影响（重要修正）

原设想是"开发 VPN 代理，拦截并伪造**所有**联网流程"。
实际研究发现**需要伪造的面比预想小得多**：

| 原设想 | 实际 |
|---|---|
| 伪造 Google 的 uncertified 接口 | ❌ **不要碰** —— 它是活的，而且注册逻辑（JS）在 App 里 |
| 伪造包清单 | ❌ **不需要** —— 清单就在 assets 里，RC4 解出来即可 |
| 伪造注册用的 `register_js` | ❌ **不需要** —— 它是硬编码常量，不在服务器 |
| 伪造更新检查响应 | ✅ 需要（但可能失败也能兜底） |
| 伪造 APK 下载源 | ✅ 需要（但有更简单的替代） |

**⇒ 真正需要"联网伪造"的只剩两处，而且第二处有更省事的做法。**

### 下载源：三种可选方案（按复杂度递增）

**方案 A（最简单）：预置 APK 到 FileDownloader 缓存目录**
让 App 认为"已下载完成"，完全不碰网络。
需要先确定 FileDownloader 的缓存命名规则（子 agent 正在查）。

**方案 B（最直接）：把 APK 内置进我们自己的 App，由我们代装**
既然 `work/gms29/` 那 5 个文件与厂商清单**逐字节一致**（已用 md5 验证），
我们自己的安装器可以直接把它们复制到设备再调 `DevicePackageManager.installPackage`。
**代价**：APK 体积 +约 120 MB。但换来的是完全不依赖任何服务器。

**方案 C（原设想）：VPN 劫持 CDN 域名到本地 HTTP 服务**
技术上可行，但要处理 FileDownloader 的分块/断点续传语义，最复杂。

**⚠️ 一个必须先问清的问题**：我们的 App 拿不到 `MDM_INSTALL_SYS_APP`（改包必死，
第一阶段已实测 0/7）。所以方案 B/C 都需要**让原始未改动的 App 来完成提权那一步** ——
或者**接受"装成普通用户应用"**。

而第一阶段已经证明：**GMS 作为普通用户应用 + Play 商城自我升级，就能拿到
`SYSTEM`/`PRIVILEGED` 标志**（Mate50 就是这样）。这条路径**不需要 MDM**。

⇒ 所以方案 B（我们代装普通应用 + 引导用户在"应用启动管理"里放行 + 让 Play 商城自我升级）
**可能是完全绕开 MDM 的一条路**。这值得在第二阶段重点验证。
