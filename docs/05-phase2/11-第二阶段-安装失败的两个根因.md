## 三、根因 ①：FileProvider 路径写死了错误的包名（潜在缺陷）

`res/xml/file_paths.xml`：

```xml
<paths>
  <cache-path    name="app_cachePath"  path="file" />
  <external-path name="download_path"  path="Android/data/com.x.plus.pro/cache/" />
                                              ↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑
</paths>
```

**发布包名是 `com.qiyecomm`，但路径里写的是开发期的 `com.x.plus.pro`。**

**为什么原版没暴露这个问题**：原版走的是 MDM 特权分支
`DevicePackageManager.installPackage(cn, path)` —— 那个 API 接受**文件系统路径**，
不需要 content:// URI，所以 FileProvider 根本没被用到。

我们的补丁把安装改成 `ACTION_VIEW` + FileProvider，**才把这个潜伏 bug 暴露出来**。

## 四、根因 ②：Intent 缺少 `FLAG_GRANT_READ_URI_PERMISSION`（真正的失败原因）

从 `wm_` 事件日志抓到了决定性证据：

```
08:57:51.368  wm_create_activity: [..., com.android.packageinstaller/.InstallStart,
                                   android.intent.action.VIEW,
                                   application/vnd.android.package-archive]
08:57:51.423  wm_set_resumed_activity: [..., InstallStart, minimalResumeActivityLocked]
08:57:51.437  wm_finish_activity: [..., InstallStart, app-request]     ← 2 毫秒后自杀
08:57:53.392  wm_destroy_activity: [..., InstallStart, finish-idle]
```

**系统安装器被正确启动了，但在 2 毫秒内自己退出** —— 它拒绝了那个 `content://` URI。

### 原因

我们的补丁构造的 Intent：

```smali
const/high16 v1, 0x10000000      # 只有 FLAG_ACTIVITY_NEW_TASK
invoke-virtual {v0, v1}, Landroid/content/Intent;->addFlags(I)Landroid/content/Intent;
invoke-virtual {v1, v0}, Landroid/content/Context;->startActivity(Landroid/content/Intent;)V
```

**缺少 `FLAG_GRANT_READ_URI_PERMISSION`（`0x00000001`）** ——
`content://` URI 必须显式把读权限授予接收方，否则安装器读不到那个 APK。

### 原版是怎么做的（对照）

原版的第一分支（MDM 路径）里**有**这个授权：

```smali
.line 119
const/4 v3, 0x1
invoke-virtual {v1, v2, v0, v3}, Landroid/content/Context;->grantUriPermission(
        Ljava/lang/String;Landroid/net/Uri;I)V
```

所以是**我们的补丁漏了这一环**，不是原版的 bug。

### 修法

```diff
-    const/high16 v1, 0x10000000
+    # FLAG_ACTIVITY_NEW_TASK | FLAG_GRANT_READ_URI_PERMISSION
+    const v1, 0x10000001
     invoke-virtual {v0, v1}, Landroid/content/Intent;->addFlags(I)Landroid/content/Intent;
```

### 1. `file_paths.xml` 的包名修复尚未完成

`fix_file_paths.py` 里的等长替换假设是错的：
`com.x.plus.pro`（14 字符）≠ `com.qiyecomm`（12 字符），
需要在二进制 XML 的字符串池里重建条目并调整 chunk 大小与后续偏移。

**但这是否是必需的一步，取决于根因②的修复效果**：

- 如果 App 把 APK 放在 `<cache-path path="file">` 覆盖的范围内 ⇒ 包名那条无关，不用改
- 如果放在外部缓存 ⇒ 必须改

**实测线索**：`/sdcard/Android/data/com.qiyecomm` **完全不存在**，
说明 App 没有写过外部存储 ⇒ 更可能在内部缓存 ⇒ **`cache-path` 已覆盖 ⇒ 也许不用改**。

### 调试手法（值得记下）

安装器"启动了又立刻退出"这种情况，**普通 logcat 看不到原因**，
要从 `wm_` 事件流里看 Activity 的创建/结束时序：

```powershell
adb shell "logcat -d -b all -t 20000" | Select-String "wm_create_activity|wm_finish_activity|InstallStart"
```

`wm_finish_activity: [..., InstallStart, app-request]` 且紧跟创建 ⇒
**接收方主动拒绝**，通常是 URI 权限或格式问题。
