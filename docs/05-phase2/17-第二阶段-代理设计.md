# 第二阶段：代理设计（完整协议 + 响应器）

> **代理要伪造的唯一端点：`POST https://api.trip-happy.com/index.php/upgrade/info/`**
>
> 本文的每个要素都是从**原版 smali** 读出来的，不是猜的。响应器已自检通过。

## 一、为什么只需要这一个端点

`SplashActivity` 启动后：

```
DeviceManage.a(ctx)                    → 华为 MDM API 检查（无网络）
UpdateInstance.e(ctx)                  → 构造请求体（无网络）
UpdateInstance.c(ctx)                  → 【唯一网络请求】api.trip-happy.com
   ├─ 成功 → 有更新列表 → 显示更新框 → 走安装
   └─ 失败 → a$1.a() → 弹「连接谷歌网络异常」
```

**启动链路不访问 Google。** `HttpUtil.a()`（那个真的去 GET `https://www.google.com`
的检查）**只在注册流程**被调用（唯一调用者 `register/c$1.run()`）——
这与用户的 HttpCanary 抓包完全一致。

## 二、完整协议

### 2.1 请求

```
POST https://api.trip-happy.com/index.php/upgrade/info/
Content-Type: 由 f/d$a 决定
连接超时 = 5000 ms   (0x1388)
读取超时 = 5000 ms
body = JSON:
{
  "uuid": "...", "brand": "HUAWEI", "model": "...",
  "product": "Trip", "time": "<ms>",
  "os": "Android", "os_version": 31,
  "language": "...", "region": "...",
  "wifi": "1" | "0",
  "version_code": "...", "version_name": "...",
  "privPermission": "...", "undetachable": "...", "addItem": "...",
  "sign": "<见下>"
}
```

**⚠️ `"wifi"` 只是请求体里的一个字段，不是门禁。**（我早先误判过。）

### 2.2 请求签名（`update/c.a(HashMap)` L100-217）

```java
String[] keys = map.keySet().toArray(new String[0]);
Arrays.sort(keys);                                  // 字典序
StringBuffer sb = c.c; sb.delete(0, sb.length());   // 复用静态 buffer，先清空
for (String k : keys) sb.append(k).append("=").append(map.get(k));
sb.append("XPP");
return StringUtil.b(sb.toString());                 // MD5
```

```
sign = MD5( "".join(k + "=" + v for k in sorted(keys)) + "XPP" )
```

### 2.3 响应

```json
{
  "data": {
    "upgradeConf":     "<base64( RC4( plainJson ) )>",
    "upgradeConfSign": "<MD5( md5hex(base64_decode(upgradeConf)) + 请求的sign )>"
  }
}
```

### 2.4 校验逻辑（`update/c$1.a(Object)`）

```java
JSONObject data = root.getJSONObject("data");
String conf  = data.getString("upgradeConf");
String sign  = data.getString("upgradeConfSign");

byte[] raw   = Base64.decode(conf);            // f/k.a(String)
String md5   = Base64Util.a(raw);              // f/a.a([B) —— 实际是 MD5 十六进制
String expect= StringUtil.b(md5 + c.g);        // c.g = 请求的 sign

if (!StringUtil.b(expect).equals(sign))  → 失败
else  d bean = gson.fromJson(conf_plaintext, beans/upgrade/d.class);
```

**三种失败都进同一个回调 `IUpdateRequestCallback.a()` → 弹窗：**

| 分支 | 触发 |
|---|---|
| `a(f/d$e)` | 网络/超时失败 |
| `:cond_ca` | 签名不匹配 |
| `catch JSONException` | 响应不是合法 JSON |

### 2.5 加解密

| 项 | 实现 |
|---|---|
| 算法 | **RC4**（`RC4Factory`，`com/x/plus/pro/b/c`） |
| 密钥 | `"abksfsijifefe"`（`update/c.b` 静态字段），`key.getBytes()` |
| 编码 | **`Base64.NO_PADDING(2) \| NO_WRAP(8)` = flags 0xa**（`f/a.a([B)`） |
| MD5 | `getBytes()` = UTF-8，逐字节小写十六进制，不足两位前置 `0` |

**✅ 实证**：`assets/Xpp_Q.json` → `base64_decode` → `RC4` → **合法 JSON，5 个包**。
`assets/Xpp_P.json` → 7 个包。（SDK==28 用 P，否则用 Q。）

### 2.6 解密后的结构

```
beans/upgrade/d               { "a": UpgradePackageModel }
  UpgradePackageModel  extends ApkBaseInfo
    downUrl fileMd5 verCode pkgName fileSize downloadPath sign_1 sign_256 number
    backgroundUpdate  { silent: boolean, notification { enable, message, title } }
    homeUpgrade       { popPrompt: boolean, message, button }
    apk               List<ApkInfo>            ← 要安装的包
```

**⇒ 直接拿厂商自己的 `Xpp_Q.json` 塞进 `apk` 字段即可。**

## 四、投递方式（三种，按代价排序）

### 方案 A：借道用户已有的梯子（**推荐先试**）

不需要写 VPN 代码。用 Clash 的 **URL 重写 / 脚本规则**：

```
把 api.trip-happy.com 的请求拦到本地 HTTP 服务
```

`trip_happy_responder.py serve` 已经能直接接这个请求并返回合法响应。

**优点**：零 Android 代码，立刻可测。
**缺点**：依赖用户的梯子能配重写规则。

### 方案 B：扩展 LZRevive 的 `ProxyVpnService`

LZRevive 已经有 VPN 服务（`ProxyVpnService.java`，含最小 IPv4/TCP 栈）。
加一个 host 匹配 + 本地响应即可。

**优点**：自包含，不依赖第三方 App。
**缺点**：要在 Java 里再实现一遍 RC4/base64/MD5（不难），而且 **HTTPS 需要中间人证书**。

> ⚠️ **HTTPS 是核心难点**。方案 A 里梯子已经做过 MITM，证书已装；方案 B 得自己处理。

### 方案 C：改 hosts + 本地 HTTPS + 自签 CA

最麻烦，且要用户装 CA 证书。**不推荐。**

## 五、⚠️ 一个尚未闭环的问题

`update/c$1` 决定「是否真的去安装」的分支：

```java
if (!c.d(ctx) && model.a().a /* backgroundUpdate.silent */) {
    c.a(ctx, (c$a) null);        // → 后台安装流程
}
```

而 `c.d(ctx)` 是：

```java
static boolean d(Context ctx) {
    String pkg = ctx.getPackageName();
    String installer = PackageUtil.b(ctx);           // 安装来源包名
    // pkg.equals(installer) && !BaseApp.a
}
```

**⇒ 这条路径依赖「安装来源」判断。** 我们的场景（改包版重装）与厂商预期可能不同。

**尚未实测**：把合法响应喂给 App 后，它到底走哪条分支。

**这正是下一步要测的** —— 因为响应器已经能产出 App 会接受的报文，
现在可以**用真实设备试**，看它是否往下走。

## 七、纠错记录（重要）

本轮之前的多次误判，值得记下：

| 错误结论 | 实际 |
|---|---|
| 「App 只认 WiFi」 | `wifi` 只是请求体字段，不是门禁 |
| 「VPN 会骗过门禁」 | 代码里没有任何 VPN 判断 |
| 「Google 检查在启动链路上」 | 它在**注册**流程（`register/c$1`） |
| 「`getAllNetworkInfo` 返回 null」 | 实测返回 15 条 |
| 「IPv6 导致启动失败」 | 探针测的是注册路径的检查 |

**教训：依据方法名/资源名猜语义是不可靠的 —— 必须追调用点。**
（`R.string.`**`register`**`_net` 的名字早就提示了它在注册流程，我看了却没往这想。）
