# 第二阶段：代理实现（已内建到 LZRevive）

> 响应器已用 Java 实现并**在真机上自检 PASS**。
> 本文回答「挂 Clash 还是内建」以及"会不会影响你现有代理配置"。

---

## 一、结论：**内建到 LZRevive，不要挂 Clash**

### Clash 方案的三个问题

| # | 问题 | 说明 |
|---|---|---|
| 1 | **功能上做不到** | Clash 的 `url-rewrite`/`script` 是**请求侧**重写。**响应体重写**只在部分 Clash Meta 构建里支持，各家 GUI 不一致。而我们要**凭空生成**一个带签名的响应，Clash 做不到 |
| 2 | **会冲突现有配置** | 要加 `api.trip-happy.com → 本地` 的规则，必须插在现有 rules **之前**。顺序改错会波及**所有**梯子流量；而且各家 GUI 的规则语法不同，容易踩坑 |
| 3 | **架构上是错的** | Clash 是**全局 VPN**。开了它，App 启动时的网络环境就变了 —— 而前面几轮实测表明，网络状态对 App 行为有影响（虽然最终证明不是门禁，但引入无关变量会让排查变难） |

**⇒ 内建方案：不碰你的 Clash，不影响任何现有配置，也不依赖第三方 App。**

## 二、已实现的部分（可用）

### 2.1 `TripHappyCrypto.java` —— 密码学

| 方法 | 对应原版 |
|---|---|
| `rc4(key, data)` / `rc4App(data)` | `RC4Factory.a("abksfsijifefe")` |
| `b64NoPad(byte[])` | `Base64Util.a([B)` = `Base64.NO_PADDING\|NO_WRAP` |
| `b64Decode(String)` | 容错解码（忽略空白、容忍缺填充） |
| `md5hex(String)` / `md5hex(byte[])` | `StringUtil.b(String)` |
| `requestSign(Map)` | `update/c.a(HashMap)` —— `MD5(sorted k=v + "XPP")` |
| `responseSign(conf, reqSign)` | `c$1` 的校验式 |
| `encodeConf` / `decodeConf` | base64 ∘ RC4 及其逆 |

**全部自实现，不依赖 `android.util.Base64`** —— 这样同一个类也能在桌面 JVM 上做离线验证。

### 2.2 `TripHappyResponder.java` —— 响应生成

```java
TripHappyResponder r = new TripHappyResponder(ctx);
String body = r.buildResponse(requestSign, /*silent=*/true);
```

- 从 `assets/Xpp_Q.json`（SDK 28 则 `Xpp_P.json`）读取厂商资产
- `plaintext = RC4( base64_decode(asset) )` —— 运行时解密
- 包成 `beans/upgrade/d { a: UpgradePackageModel }`，含 `apk[]` + `backgroundUpdate{silent,notification}` + `homeUpgrade{popPrompt,message,button}`
- `bg.silent = true` —— 这是走安装分支的必要条件

## 三、还剩的最后一块：TLS 中间人

### 3.1 为什么绕不过

| 检查项 | 结果 | 结论 |
|---|---|---|
| 请求 URL | `https://api.trip-happy.com/index.php/upgrade/info/` | **是 HTTPS** |
| `usesCleartextTraffic` | `true` | 无关 |
| `networkSecurityConfig` | **不存在** | ✅ **App 信任用户安装的 CA** |
| `targetSdkVersion` | 29 | 同上 |
| 证书放行代码 | **完全没有** | 用系统默认校验 ⇒ **必须中间人** |

### 3.2 可行（因为信任用户 CA）

`ProxyVpnService` 已有：
- `VpnService` + 最小 IPv4/TCP 栈
- DNS 层劫持：把目标域名映射到 `VPN_ADDR`

**缺的只是 TLS 服务端。** 需要：
1. 生成一张 CA（或用设备上已有的）
2. 用 CA 签一张 `api.trip-happy.com` 的服务端证书
3. 在 `ProxyVpnService` 的 443 响应路径里做 TLS 握手
4. 把解密出的请求体交给 `TripHappyResponder`，把响应加密回去

### 3.3 ✅ 好消息：设备上可能已有可用的 CA

```
package:com.reqable.android      ← 你抓包用的 Reqable（小黄鸟），还在
```

**你装的那份 CA 证书仍在系统的用户证书库里**，而 App 信任用户 CA。

**但 CA 私钥在 Reqable 的沙箱里**（`/data/data/com.reqable.android/files/`），adb 读不到。

**三条路：**

| 路线 | 做法 | 代价 |
|---|---|---|
| **A** | 让 LZRevive 用它**自己的 CA**，用户手动装一次 | 要装一次证书（设置里点几下） |
| **B** | 把 LZRevive 的 CA 推成**系统证书** | 需 root 或 `adb root` —— **本机没有** |
| **C** | 从 Reqable 沙箱导出它的 CA 私钥 | 需 root 或 Reqable 支持导出 —— **待确认** |

**⇒ 最实际的是 A**：LZRevive 首次启动时生成 CA 并导出 `.crt`，用户装一次即可。

## 四、⚠️ 两个尚未验证的前提

### 4.1 `c.d(ctx)` 分支

`update/c$1` 决定是否走安装：

```java
if (!c.d(ctx) && model.a().a /* backgroundUpdate.silent */) {
    c.a(ctx, null);      // → 后台安装流程
}
```

而 `c.d(ctx)` 比较**安装来源包名**与自己的包名。**我们的重装场景与厂商预期可能不同，未实测。**

### 4.2 APK 从哪来

`Xpp_Q.json` 里的 `downUrl` 指向**已死的 CDN**。但**实测证明不需要联网** ——
APK 从 `assets/` 本地解包（原版自带全套，MD5 与清单 5/5 一致）。

**⇒ 代理只需处理更新接口，不必处理 CDN。**

## 五、当前进度与下一步

```
✅ 协议逆向完成（100% 从原版 smali 读出）
✅ Java 密码学实现（真机自检 PASS）
✅ 响应生成（真机自检 PASS）
✅ 厂商资产打包进 LZRevive
⬜ TLS 中间人（需 CA 证书）
⬜ ProxyVpnService 接入响应器
⬜ 端到端实测
```

**下一步二选一：**

**① 先做 TLS + 端到端**（技术闭环，但要你装一次证书）
**② 先用更省事的办法验证「响应能否让 App 越过弹窗」** —— 例如用 Reqable 的
「响应重写」功能手动粘一份 `buildResponse` 的输出进去

**② 的价值**：能在**不写 TLS 代码**的前提下，直接回答「响应有效吗」
以及「`c.d(ctx)` 走哪条分支」。**如果响应无效，TLS 那部分就白做了。**

**我建议先做 ②。** 你手上有 Reqable，把响应体粘进它的重写规则即可。
