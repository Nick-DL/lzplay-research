# 第二阶段：安装失败的第 3 个原因 —— 清单缺少 `REQUEST_INSTALL_PACKAGES`

> **本轮做了"从零环境"的真实测试，一路排掉三个障碍，最后卡在一个原版从来不需要的权限上。**

---

## 二、三个障碍与排除过程

### 障碍 ① OOM（已修，见 `10-`）

`FileUtil.b()` 整包读入算 MD5 → 86 MB 文件 → 256 MB 分配 → 启动即崩。
改成 8 KB 流式后消失。

### 障碍 ② Intent 缺 `FLAG_GRANT_READ_URI_PERMISSION`（已修）

`wm_` 事件流显示安装器启动后 **2 毫秒**就自己退出。
原版第一分支有 `grantUriPermission(..., 1)`，我们的 `ACTION_VIEW` 补丁漏了。
加上 `0x10000001` 后，URI 与标志都正确了：

```
wm_create_activity: [..., InstallStart,
    android.intent.action.VIEW,
    application/vnd.android.package-archive,
    content://com.qiyecomm.provider/app_cachePath/com.google.android.gms_29.apk,
    276824065]        # 0x10800001
```

**顺带确认**：FileProvider 走的是 `app_cachePath`（**内部缓存**），
所以 `file_paths.xml` 里那个 `com.x.plus.pro` 包名 bug **不影响**，不用修。

### 障碍 ③（当前卡点）清单缺少 `REQUEST_INSTALL_PACKAGES`

## 三、决定性的对照实验

把**同一个** APK 用另一条路装：

```powershell
adb push work\gms29\com.google.android.gms_29.apk /data/local/tmp/gms_test.apk
adb shell pm install -r -d /data/local/tmp/gms_test.apk
→ Success
→ package:com.google.android.gms          ✅
```

**⇒ APK 有效、签名没问题、系统没有阻止安装、存储空间充足。**

**⇒ 问题 100% 在 `InstallStart` 这条 intent 路径上**，而 `pm install` 走的是
PackageInstaller 的**会话 API**，完全绕开它。

## 四、根因判断：`REQUEST_INSTALL_PACKAGES` 未声明

### 证据链

**1) 清单里只申请了华为的特权安装权限**

```
requested permissions 里的安装相关项：
  com.huawei.permission.sec.MDM_INSTALL_SYS_APP            ← 华为特权
  com.huawei.permission.sec.MDM_INSTALL_UNDETACHABLE_APP   ← 华为特权
  （没有 android.permission.REQUEST_INSTALL_PACKAGES）
```

**2) appops 里它是默认值**

```
appops get com.qiyecomm REQUEST_INSTALL_PACKAGES
  → Default mode: default
```

**3) 试图授权时的报错暴露了它不在清单里**

```powershell
adb shell pm grant com.qiyecomm android.permission.REQUEST_INSTALL_PACKAGES
→ SecurityException: Permission android.permission.REQUEST_INSTALL_PACKAGES
  requested by com.qiyecomm ...        # 即：该 app 未在清单中申请此权限
```

**4) 用 appops 强行设成 allow 后，行为完全没变**

```
appops set com.qiyecomm REQUEST_INSTALL_PACKAGES allow
→ REQUEST_INSTALL_PACKAGES: allow       （已生效）

再点【重试】：
  09:14:50.999  wm_create_activity: [..., InstallStart, VIEW, ...]
  09:14:51.068  wm_finish_activity: [..., InstallStart, app-request]   ← 69ms 后退出
```

**⇒ 对未声明该权限的应用，appops 的覆盖不生效** —— 这恰好印证了根因。

### 为什么原版不需要它

原版走 **`DevicePackageManager.installPackage(cn, path)`** —— 华为 MDM 特权安装，
**是绕开 Android 标准安装流程的**，因此从来不需要 `REQUEST_INSTALL_PACKAGES`。

**又是同一个模式**：特权路径掩盖了一个标准路径必须有的东西。
我们的补丁把安装改到标准路径后，这个缺失就暴露了。

## 五、两条解决路径

### 路径 A（最快，无需改包）：用会话 API 代装

既然 `pm install` 已验证可行，用户可以：

```
① 让旅游助手把内置 APK 解出来（它在内部缓存，adb 读不到 → 需要 App 自己导出）
② 或者直接用我们手里的同一套包（MD5 与厂商清单 5/5 一致）：
     work/gms29/*.apk
```

```powershell
for %f in (com.google.android.gms_29 com.google.android.gsf_29 ^
           com.google.android.syncadapters.contacts_29 com.oversea.gmapjar_29 ^
           com.android.vending_29) do adb install -r -d "%f%.apk"
```

**这条路的代价**：绕过了旅游助手的流程，用户还是要"自己准备 APK" ——
**等于回到第二阶段要解决的问题本身**。

### 路径 B（正解）：改包时把权限加进清单

给 `AndroidManifest.xml` 加一行：

```xml
<uses-permission android:name="android.permission.REQUEST_INSTALL_PACKAGES" />
```

**代价**：改清单不能再用"只换 classes.dex"的方式（当前重建脚本的策略），
必须让 aapt2 重新 link —— 而它要处理 120 MB 的 assets，风险与耗时都高。

**替代做法**：直接修改二进制 `AndroidManifest.xml` 里的 XML chunk，
在字符串池中插入新字符串、加一个 `<uses-permission>` 元素、修正 chunk 大小。
比重建整个 APK 安全。

## 七、调试手法备忘

**安装器"启动后立刻退出、零日志"时**，普通 logcat 什么也看不到。
有效手段：

```powershell
# 1) Activity 时序（判断是"接收方主动拒绝"还是"系统拒绝"）
adb shell "logcat -d -b all -t 30000" | Select-String "InstallStart|wm_finish_activity"

# 2) 对照实验：换一条安装路径（pm install 走会话 API，绕开 InstallStart）
adb push <apk> /data/local/tmp/t.apk ; adb shell pm install -r -d /data/local/tmp/t.apk

# 3) 权限三连查
adb shell "dumpsys package <pkg> | Select-String -Pattern 'granted|requested'"
adb shell appops get <pkg> REQUEST_INSTALL_PACKAGES
adb shell pm grant <pkg> android.permission.REQUEST_INSTALL_PACKAGES   # 未声明会报错，这本身就是线索
```

**关键判据**：`wm_finish_activity: [..., <Activity>, app-request]` 紧跟创建
⇒ **接收方自己退出**，优先怀疑权限或 URI 格式，而不是系统策略。
