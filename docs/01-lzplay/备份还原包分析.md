## 二、解密（我实现了完整密钥链）

Huawei KoBackup v4 格式：

```
key  = PBKDF2-SHA256(password, pwkey_salt[:16], 5000, 32)
bkey = AES-256-GCM(key, nonce = pwkey_salt[16:]).decrypt(e_perbackupkey)[:32]
校验 : PBKDF2-SHA256(bkey, checkMsg[32:], 32, 5000) == checkMsg[:32]
mkey = PBKDF2-SHA256(bkey, encMsgV3[:32], 5000, 32)
明文 = AES-256-CTR(mkey, iv = encMsgV3[32:])
```

**踩过的坑**：我一开始用 `aes-128-ctr`（把 32 字节 mkey 截成 16），产出全是随机数据。
换 **`aes-256-ctr`** 立刻成功。子 agent 笔记里写的 "AES-CTR(128-bit counter)"
说的是**计数器宽度**，不是密钥长度 —— 这个歧义坑了一轮。

工具：`work/tools/hwbackup_dec.cjs`、`hwbackup_try.cjs`（多变体试错）

## 三、★★ 备份数据里到底有什么 —— 用户假设的证实

`com.lzplay.helper.tar` 解开后有 **105 个条目**，目录结构就是 App 的 `data/data/com.lzplay.helper/`。

### 3.1 关键文件：`shared_prefs/com.lzplay.helper.xml`（5258 字节）

```xml
<string  name="sf_id">3864249757054258402</string>                  ← ★ GSF ID 已缓存
<boolean name="com.lzplay.helper.userRegistered"  value="true" />   ← ★ 已注册
<boolean name="com.lzplay.helper.register_result" value="true" />   ← ★ 注册成功
<long    name="com.lzplay.helper.checkTimeStamp"  value="1569924447161" />
<string  name="cookies">SID=pAcll6h…; HSID=A198ianv…; SSID=A_K8NJau…;
                        APISID=…; SAPISID=…; NID=188=…; CONSENT=YES+HK.zh-CN…</string>
<string  name="com.lzplay.helper.updateModel">{ …完整包清单… }</string>
```

**这就是用户推断的机制**：恢复应用数据后，lzplay 启动时看到
`userRegistered=true` + 已有 `sf_id` + 已保存的 Cookies，
**直接跳过注册流程** —— 而那正是需要联网、会卡住的环节。

> 教程的原话佐证：**"激活后不需要点击开始下载，直接返回桌面"** ——
> 因为数据里已经有全部状态，不需要走那条网络路径。

#### ★★ `presetPath = /product/priv-app/` 是本次最重要的发现

**lzplay 的设计意图就是把这些包装到系统分区 `/product/priv-app/`（特权系统应用目录）。**

这印证了之前从 framework 反编译得出的结论：

```
trustspace 三道闸门
  闸门 1 (iaware)  ← 应用启动管理策略
  闸门 3 (sticky)  ← caller 是系统应用 && 目标不是系统应用 ⇒ 拦截
```

**把 GSF 装成系统应用 ⇒ 闸门 1 和闸门 3 同时失效 ⇒ provider 能起来。**

这就回答了之前那个"GSF provider 起不来"的死结 —— **不是要绕过它，而是要让 GSF 本身变成系统应用。**

## 五、`GMSAPKS` 与 lzplay 清单的差异（重要）

lzplay 的 `updateModel` 期望 **6 个包**，而教程提供 **7 个不同名字的包**：

| lzplay 期望 | 教程提供 | 备注 |
|---|---|---|
| `com.google.android.gms` v18381046 | `6-Google Play 服务.apk` | 版本差很多（2019 vs 2026） |
| `com.google.android.gsf` v29 | `5-V12/V10谷歌服务框架.apk` | 教程**最后要把它 disable** |
| `com.google.android.gms.policy_sidecar_aps` | `3-Policy sidecar aps.apk` | ✓ |
| `com.google.android.syncadapters.contacts` v29 | `2-V12/V10谷歌通讯录.apk` | ✓ |
| `com.apkmirror.gmapjar` | — | 教程没提供 |
| `com.android.vending` | `7-Google Play 商店.apk` | 版本差很多 |
| — | `1-google账户管理.apk` | lzplay 清单里没有 |
| — | `4-Shared Library.apk` | lzplay 清单里没有 |

⇒ **教程并不是让 lzplay 自己装包**，而是：
1. 用 lzplay 的备份还原**只为了拿到 MDM 权限**（激活"谷歌服务助手"）
2. **然后手动装新版 GMS APK**
3. 最后 `pm disable-user com.google.android.gsf` 消除认证弹窗

**这是关键理解**：lzplay 在新教程里的角色是"**开权限的工具**"，
不是"装 GMS 的工具"。它的 `updateModel` 和 `/product/priv-app/` 逻辑基本不再使用。

## 六、对整体结论的修正

| 之前的理解 | 修正后 |
|---|---|
| 要用 lzplay 自己的流程装 GMS | ❌ 教程只用 lzplay **拿权限**，GMS 手动装新版 |
| GSF provider 起不来 = GMS 不可用 | ❌ 教程**主动禁用 GSF**，现代 GMS 不依赖它 |
| lzplay 卡启动页是死结 | ✅ 备份数据（`userRegistered`/`sf_id`）可绕过 |
| trustspace 是主要障碍 | ⚠️ 只影响 GSF provider；禁用 GSF 后不构成障碍 |

**用户的核心判断全部正确。**
